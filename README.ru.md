MWS IOPS Autoscaler — внешний агент для **MWS Cloud Compute**, который отслеживает реальную нагрузку
на подключенные диски NBS-PL2 и подстраивает под нее лимит IOPS. Когда диск упирается в лимит, агент
повышает его. Когда нагрузка долго остается низкой, агент снижает лимит, чтобы вы не платили за
неиспользуемый запас.

Агент подходит для нагрузок, потребность которых в дисковой производительности меняется со временем.
Вместо того чтобы сразу выделять IOPS под пиковую нагрузку, задайте допустимый диапазон, и агент
будет держать лимит в его пределах по фактической нагрузке.

[Документация в каталоге docs](docs/README.md) доступна только на английском языке.

## Как работает агент

На каждой целевой ВМ MWS работает свой экземпляр агента. В каждом цикле агент:

1. Определяет ВМ MWS, на которой запущен.
2. Находит подключенные к ней диски NBS-PL2 и определяет способ подключения каждого:
   [зависимый или независимый](https://mws.ru/docs/cloud-platform/compute/general/disks-spec-ref-overview.html).
3. Собирает статистику ввода-вывода каждого диска из `/proc/diskstats`.
4. Дожидается заполнения окна наблюдения и по загрузке, очереди и задержкам определяет, перегружен
   диск или долго простаивает.
5. Рассчитывает нужный лимит IOPS и меняет его через соответствующий метод MWS Compute API.
6. Записывает решение в журнал и публикует состояние и метрики Prometheus.

### Текущие возможности

| Возможность | Поведение |
|---|---|
| Облако и тип диска | MWS Cloud Compute, подключенные диски NBS-PL2 |
| Модель развертывания | Один локальный агент на каждой целевой ВМ с Linux |
| Направление изменений | В обе стороны: повышает лимит при перегрузке, снижает после долгого простоя |
| Метрики | Метрики гостевой ОС из `/proc/diskstats` |
| Выбор дисков | Автоматический поиск с исключениями или явный список |
| Защитные механизмы | Границы для каждого диска, округление до 100 IOPS, пауза между изменениями, лимит изменений за последние 24 часа, защита от одновременных изменений, пробный запуск |
| Ресурсы ВМ | Учитывает общий для ВМ пул IOPS `3000 × vCPU` и нагрузку соседних дисков |
| Эксплуатация | Журнал решений в формате JSON Lines, метрики Prometheus, эндпоинты liveness и readiness |

## Пререквизиты

- Подключите сервис Compute в проекте MWS Cloud.
- Создайте ВМ MWS с Linux и подключите к ней хотя бы один диск NBS-PL2. Убедитесь, что гостевая ОС
  показывает каждый управляемый диск как `/dev/disk/by-id/mws-<device_name>` и предоставляет
  `/proc/diskstats`.
- Создайте сервисный аккаунт, выдайте ему роль `compute.editor` в проекте и привяжите его к ВМ. Если
  агент будет управлять зависимыми дисками, выдайте сервисному аккаунту также роль
  `iam.serviceAccount.admin` на этот же сервисный аккаунт.
- Убедитесь, что из ВМ доступны сервис метаданных по адресу `169.254.169.254` и API MWS по адресу
  `https://api.mwsapis.ru`.
- Чтобы собрать агент из исходного кода, установите Go 1.26 или новее и Git.
- Подготовьте постоянный каталог с правом записи для учета изменений за 24 часа. По умолчанию —
  `/var/lib/mws-iops-autoscaler`.

## Быстрый старт

Начните с интерактивного пробного запуска на целевой ВМ. Агент найдет диски, соберет метрики и
примет решения, но не изменит лимиты IOPS.

### 1. Подготовьте ресурсы MWS

1. В консоли MWS подключите Compute в проекте и создайте сервисный аккаунт.
2. В разделе IAM проекта выдайте сервисному аккаунту роль `compute.editor`.
3. Если агент будет управлять зависимыми дисками, откройте **IAM → Сервисные аккаунты**,
   выберите сервисный аккаунт агента, на вкладке **Доступы к ресурсу** выдайте этому же сервисному аккаунту роль
   `iam.serviceAccount.admin`.
4. [Привяжите сервисный аккаунт к ВМ](https://mws.ru/docs/cloud-platform/compute/general/vm-link-sa.html)
   в консоли или через MWS CLI:

   ```bash
   mws compute vm update <vm-name> --service-account <service-account>
   ```

   Здесь:

   - `<vm-name>` — имя целевой ВМ.
   - `<service-account>` — сервисный аккаунт агента.

### 2. Проверьте ВМ

Выполните команды внутри целевой ВМ:

```bash
# Проверить, что привязанный сервисный аккаунт получает токен из метаданных.
curl -fsS -o /dev/null \
  -H 'Metadata-Flavor: Google' \
  http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token

# Проверить, что ядро предоставляет счетчики дисков.
test -r /proc/diskstats
```

### 3. Соберите бинарный файл

```bash
git clone https://github.com/rodion1010/mws-iops-autoscaler.git
cd mws-iops-autoscaler
mkdir -p bin
go build -o bin/mws-iops-autoscaler ./cmd/mws-iops-autoscaler
```

Бинарный файл можно собрать на другой машине под архитектуру целевой ВМ с Linux и скопировать на ВМ.

### 4. Создайте конфигурацию

Сохраните пример ниже в файл `config.yaml`. В примере исключен загрузочный диск с `device_name`
`mws-bootdisk`. Замените это значение на `device_name`
загрузочного диска из статуса вашей ВМ. Остальными поддерживаемыми дисками ВМ агент управляет
автоматически:

```yaml
version: 1
mode: local

policy:
  limits:
    min_iops: 1000
    max_iops: 10000

disks:
  mode: auto-discovery
  exclude:
    - mws-bootdisk

runtime:
  metrics:
    source: guest
    collection_interval: 10s
  controller:
    reconcile_interval: 30s
    discovery_interval: 5m
```

Чтобы агент управлял только выбранными дисками, перечислите их явно:

```yaml
disks:
  mode: selected
  policies:
    mws-datadisk: {}
```

Правила валидации, лимиты для отдельных дисков и экспериментальные параметры `advanced` описаны в
[справочнике по конфигурации](docs/configuration.md). Оставьте значения по умолчанию, пока данные
пробного запуска не покажут, что их нужно менять.

### 5. Проверьте конфигурацию

```bash
./bin/mws-iops-autoscaler \
  -config ./config.yaml \
  -validate-config
```

Если конфигурация корректна, команда завершается с кодом 0 и выводит сводку в одну строку. Если нет —
завершается с кодом 1 и выводит все найденные ошибки.

### 6. Запустите агент в пробном режиме

Создайте локальный каталог состояния и запустите агент:

```bash
mkdir -p ./var

./bin/mws-iops-autoscaler \
  -config ./config.yaml \
  -dry-run \
  -state-dir ./var \
  -journal ./decisions.jsonl \
  -listen 127.0.0.1:9435
```

Оставьте агент работать хотя бы на одно полное окно наблюдения. Со значениями по умолчанию для решения
о повышении нужно 5 минут данных, для решения о снижении — 30 минут. Создайте нагрузку, похожую на
рабочую, и посмотрите в журнале предложенные изменения и причины, по которым агент ничего не менял:

```bash
tail -f ./decisions.jsonl
```

В пробном режиме агент не меняет IOPS дисков. Для независимых дисков он может попросить API проверить
предложенное изменение. Для зависимых дисков агент проверяет решение локально.

### 7. Проверьте состояние и метрики

В другом окне терминала выполните:

```bash
curl -fsS http://127.0.0.1:9435/healthz
curl -fsS http://127.0.0.1:9435/readyz
curl -fsS http://127.0.0.1:9435/metrics | head
```

`/healthz` возвращает HTTP 200, пока процесс работает. `/readyz` возвращает HTTP 200, только если
выполнены все условия:

- конфигурация корректна;
- поиск дисков завершился успешно и список управляемых дисков не пуст;
- последний сбор метрик завершился успешно;
- сохраненный учет изменений исправен.

Иначе `/readyz` возвращает HTTP 503 с подробностями в JSON. Даже при успешном сборе метрик по
отдельному диску может не быть данных: причины `no_data` и устаревших данных ищите в журнале решений.

### 8. Включите изменение IOPS

Когда решения пробного режима совпадут с ожиданиями, остановите процесс и запустите его без
`-dry-run`:

```bash
./bin/mws-iops-autoscaler \
  -config ./config.yaml \
  -state-dir /var/lib/mws-iops-autoscaler \
  -journal /var/log/mws-iops-autoscaler-decisions.jsonl \
  -listen 127.0.0.1:9435
```

У пользователя процесса должно быть право создавать оба пути и писать в них. Сохраняйте каталог
состояния между перезапусками: в файле `budget.jsonl` хранится учет изменений, на котором держится лимит
изменений за 24 часа.

> [!WARNING]
> Измененный лимит IOPS остается в MWS после остановки агента. Агент не возвращает прежний лимит и не
> снижает его при остановке. Быстро перезапустите агент или измените лимит диска вручную.

Запускайте бинарный файл под своим менеджером процессов:

- запускайте ровно один агент на целевую ВМ;
- перезапускайте при сбое и останавливайте сигналом `SIGTERM`;
- сохраняйте каталог состояния;
- собирайте журнал решений и метрики с `/metrics`;
- не открывайте HTTP-порт в интернет без защиты на уровне сети.

## Основные параметры конфигурации

- `policy.limits.min_iops` и `max_iops` задают допустимый диапазон. Диски MWS NBS-PL2 принимают
  1000–10000 IOPS с шагом 100.
- `disks.mode: auto-discovery` — агент управляет всеми найденными поддерживаемыми дисками, кроме
  перечисленных в `exclude`.
- `disks.mode: selected` — агент управляет только дисками из `selected`.
- Имена дисков — это значения `device_name` в MWS вместе с префиксом `mws-`, а не пути `/dev` в Linux.
- Класс подключения диска агент определяет сам, способ изменения настраивать не нужно.
- `runtime.metrics.source` — `guest`.
- Агент ничего не меняет, если:
  - метрики или результаты поиска дисков устарели;
  - окно наблюдения не заполнено;
  - диск не перегружен и не простаивает все окно;
  - действует пауза между изменениями или исчерпан лимит изменений;
  - не удалось подтвердить, что это тот же диск;
  - соседние диски оставляют ВМ слишком мало свободных IOPS.

## Параметры командной строки

| Параметр | Описание | По умолчанию |
|---|---|---|
| `-config <path>` | Файл конфигурации, обязательный | — |
| `-validate-config` | Проверить конфигурацию и завершить работу | выключен |
| `-dry-run` | Найти диски, собрать метрики и принять решения без изменений | выключен |
| `-state-dir <path>` | Постоянный каталог для учета изменений за 24 часа | `/var/lib/mws-iops-autoscaler` |
| `-journal <path>` | Журнал решений в формате JSON Lines | stdout |
| `-listen <addr>` | Адрес для `/metrics`, `/healthz` и `/readyz` | `:9435` |

Перед запуском агент в локальном режиме получает проект, зону и имя ВМ из сервиса метаданных ВМ.
MWS Go SDK отдельно получает учетные данные привязанного к ВМ сервисного аккаунта, тоже через сервис
метаданных.

## Мониторинг

В каждом цикле агент пишет в журнал решений по одному JSON-объекту на каждый управляемый диск. В объекте
есть текущий и предложенный лимит IOPS, действие, причина, загрузка, нагрузка, задержка, свободные IOPS
ВМ, заполненность окна и остаток лимита изменений. Чтобы понять, почему агент изменил диск или оставил
его как есть, смотрите сначала журнал.

Агент публикует метрики Prometheus, в том числе:

- `iops_autoscaler_disk_provisioned_iops` и `iops_autoscaler_disk_proposed_target_iops`;
- `iops_autoscaler_disk_observed_iops`, загрузку, перегрузку и нагрузку диска;
- `iops_autoscaler_vm_headroom_iops` и `iops_autoscaler_vm_cap_reached`;
- свежесть данных, заполненность окна и остаток лимита изменений;
- пропущенные диски, диски из конфигурации, которыми агент не управляет, и исправность учета изменений.

Полный набор метрик и сигналы для алертов описаны в разделе [Observability](docs/design.md#7-observability)
архитектурной документации. Готовых правил алертов в репозитории нет: настройте мониторинг нужных
сигналов сами. Ответственность и условия алерта для диска, который перестал находиться, описаны в
разделе [Health and alerting](docs/design.md#73-health-and-alerting) архитектурной документации.

## Решение проблем

| Проблема | Что проверить |
|---|---|
| Не удается определить ВМ или получить учетные данные | Запустите агент внутри целевой ВМ MWS. Проверьте привязанный сервисный аккаунт и доступ к метаданным, как в [шаге 2](#2-проверьте-вм) |
| Compute API возвращает 403 | Проверьте, что Compute подключен и у сервисного аккаунта есть роль `compute.editor`. Для зависимого диска проверьте также роль `iam.serviceAccount.admin` из [шага 1](#1-подготовьте-ресурсы-mws) |
| `/readyz` показывает `discovery_succeeded: false` | Проверьте доступ к API, права и что хотя бы один подключенный поддерживаемый диск подходит под выбор в конфигурации |
| `/readyz` показывает `source_reachable: false` | Проверьте `/proc/diskstats` и символические ссылки `/dev/disk/by-id/mws-<device_name>` |
| В `/readyz` есть `configured_disks_unmanaged` | Имя из `selected` или `exclude` больше не соответствует диску. Исправьте имя или подключение диска. Это частичная деградация: агент остается готовым Условия алерта: [контракт](docs/design.md#73-health-and-alerting) |
| Агент ничего не меняет | Дождитесь заполнения окна наблюдения и посмотрите причину в поле `reason` журнала: например, диск не перегружен и не простаивает или сработал защитный механизм |
| `budget_healthy: false` | Агент не может доверять сохраненному учету изменений. Исправьте права доступа или ошибки файловой системы и перезапустите агент |
| Лимит диска на максимуме, а нагрузка остается высокой | Проверьте максимум для диска и метрику `iops_autoscaler_vm_cap_reached`. Если исчерпан общий пул IOPS ВМ, добавьте vCPU |
