# Метрики диска: нет очереди на чтение, очередь на запись в байтах, quota_utilization всегда 0

**Компонент:** NBS / экспорт метрик Compute
**Приоритет:** высокий — блокирует построение автоскейлера IOPS
**Проект для воспроизведения:** `example-project`, ВМ `iops-test-vm` (`base-2-8`), диск `datadisk` (NBS-PL2, 10 ГБ, лимит 1000 IOPS)

## Проблема

Три пробела в наборе `compute_vm_disk_*`, из-за которых по метрикам нельзя определить, что диск упёрся в лимит.

### 1. Метрики очереди на чтение нет вообще

Есть только запись:

```
compute_vm_disk_write_queue_length
compute_vm_disk_write_queue_length_max
```

Read-аналога нет. Для read-heavy нагрузок (реплики БД, аналитика) сигнал насыщения по очереди недоступен — остаётся только гистограмма латентности, у которой нет порога «нормально/плохо» без базовой линии по конкретному диску.

**Нужно:** `compute_vm_disk_read_queue_length` и `_max` с той же семантикой и метками.

### 2. Очередь измеряется в байтах, а документация обещает штуки

[disks-monitoring.html](https://mws.ru/docs/cloud-platform/compute/general/disks-monitoring.html) описывает метрику как «количество незавершенных запросов ввода-вывода (I/O requests), которые ожидают очереди на обслуживание диском» — то есть счётчик запросов.

Замер показывает, что значение меняется при смене размера блока на одной и той же глубине очереди (`iodepth=64 numjobs=4`):

| | `bs=4k` | `bs=64k` |
|---|---|---|
| `write_queue_length` | 5461 | 34065 |
| `write_queue_length_max` | **16384** | **131072** |

`16384` = 16 КиБ, `131072` = 128 КиБ. Глубина очереди в guest при этом одна и та же — `iostat` показывает `aqu-sz = 135.81`. Значит метрика байтовая, а не штучная, и не совпадает ни с документацией, ни с `aqu-sz`.

**Нужно:** очередь в штуках (количество запросов), сопоставимая с `aqu-sz` в гостевой ОС. Байтовый вариант тоже полезен — но как отдельная метрика с честным именем, а не под видом счётчика запросов.

### 3. `*_quota_utilization` всегда 0

```
compute_vm_disk_ops_peak_quota_utilization
compute_vm_disk_bytes_peak_quota_utilization
```

Обе возвращают `0` во всех замерах: на 50% нагрузки, на 100% насыщении, на чтении и на записи, на обоих дисках ВМ. Ни одного ненулевого значения за ~2 часа тестов.

Это самый обидный пункт: метрики названы ровно под эту задачу — прямой аналог `Storage IO Percent` в Azure — и не работают. Из-за этого каждый потребитель вынужден сам считать `ops_peak / spec.iops`, отдельно ходя в Compute API за спецификацией диска.

## Почему это важно: пример, где IOPS-метрика врёт

Нагрузка `randwrite bs=64k iodepth=64 numjobs=4` на диске с лимитом 1000 IOPS.

Что отдают метрики:

```
compute_vm_disk_write_ops_peak    513          → 51% от лимита 1000, «есть запас»
compute_vm_disk_write_bytes_peak  33 619 968   → 33 МБ/с
```

Что на самом деле (`iostat -dx` в гостевой ОС):

```
w/s=512  wkB/s=32768  aqu-sz=135.81  %util=100.00  w_await=265ms
```

Диск загружен на 100%, очередь 135 запросов, задержка записи 265 мс. Упёрлись не в IOPS, а в полосу: для NBS-PL2 `1000 IOPS × 32 КБ / 1024 = 31,25 МБ/с`, и 33 МБ/с — это потолок.

Автоскейлер, смотрящий на `write_ops_peak`, увидит 51% и решит, что скейлить не надо. Метрики, которые показали бы правду — `bytes_peak_quota_utilization` (пункт 3) и очередь в штуках (пункт 2) — либо равны нулю, либо в других единицах.

## Как воспроизвести

```bash
# ВМ base-2-8, диск NBS-PL2 1000 IOPS, raw-устройство без ФС
fio --name=w --filename=/dev/sdb --rw=randwrite --bs=64k --iodepth=64 --numjobs=4 \
    --ioengine=libaio --direct=1 --time_based --runtime=300

# подождать ~150 с (окно усреднения 60 с + задержка публикации ~75 с)
curl -H "Authorization: Bearer <API-ключ с monitoring.metricExporter>" \
  'https://monitoring.mwsapis.ru/metrics/v1/projects/<проект>/serviceMetrics/compute:exportPrometheusMetrics' \
  | grep -E 'queue_length|quota_utilization|write_ops_peak'
```

Повторить с `--bs=4k` и сравнить `write_queue_length_max`: 16384 против 131072 при одинаковой глубине очереди.

## Что просим

1. Добавить `compute_vm_disk_read_queue_length` / `_max`.
2. Добавить очередь в штуках для чтения и записи; байтовую оставить, но переименовать так, чтобы единица была явной.
3. Починить `ops_peak_quota_utilization` и `bytes_peak_quota_utilization` — либо убрать, если они не поддерживаются, чтобы не вводить в заблуждение.
4. Поправить описание метрики очереди в документации под фактические единицы.
